## 背景

### 业务问题

Aetheris-MemOS 定位为企业级可售卖的 AI Agent 记忆管理系统。2026-08-03 架构审查确认：

1. **技术选型合理**（Axum + PostgreSQL + Qdrant + OTel），无根本性错误。
2. **ADR 体系完善**（8 篇 ADR 覆盖租户隔离、outbox、MCP 沙箱、HA 选型、多协议鉴权、自适应学习），设计质量高。
3. **但"声明 > 实现"差距仍然存在**：核心卖点"自适应调度"是启发式+写死常量；MCP 沙箱是 mock；三协议是空壳；enterprise 假集群仍暴露活路由。

### 触发原因

- 项目需要从 MVP 进入企业级可售卖状态。
- 已有 delivery-plan（2026-07-16）按 P0→P3 分阶段规划了修复路径。
- P0 清理**大部分已执行**（假集群删除、mutator 停用、文档诚实化），但有遗留。
- 本次 intake 目标：**全线推进 P0 遗留 → P1 → P2 → P3**，确认优先级、缺口和资源约束。

## 目标与成功标准

### 业务目标

1. 系统能在企业技术尽调中通过——代码行为与文档声明一致，无"声明>实现"。
2. 多租户数据隔离由数据库层强制（RLS），而非仅依赖应用层过滤。
3. MCP 工具调用具备真实的鉴权 + 授权 + 审计（Plane A），非 mock 沙箱。
4. 所有对外暴露的协议（REST/MCP/gRPC/WS/A2A）统一受鉴权保护。
5. "自适应记忆调度"要么由 eval 证明显著优于静态配置，要么诚实降级。

### 成功标准

| 指标 | 目标值 |
|------|--------|
| P0：对外声明与代码实现一致性 | 100%（grep "声明>实现" = 0） |
| P1：跨租户负向测试通过 | 全部 memory-owned tables |
| P1：MCP call_tool 验签 + 越权拒绝 | 负向测试通过 |
| P1：备份/恢复演练通过 | PG + Qdrant |
| P2：三协议端到端真实记忆操作 | 非假数据、受鉴权 |
| P3：eval 报告产出 | 自适应 vs 静态最优，统计显著或诚实降级 |

## 用户故事

### US-1：企业买家技术尽调

**作为**企业采购决策者，**我希望**在技术尽调中验证系统的能力声明与实际代码行为一致，**以便**评估是否满足企业级要求。

**验收标准**：
- 代码中不存在 mock/占位代码冒充真实能力。
- 所有对外 API 端点返回真实数据，非 format! 字符串或写死常量。
- 文档中的能力描述与代码实现一一对应。

### US-2：多租户数据安全

**作为**SaaS 运营者，**我希望**租户间数据隔离由数据库层强制，**以便**即使应用层代码有遗漏也不会导致跨租户数据泄露。

**验收标准**：
- PostgreSQL RLS 对所有 memory-owned tables 生效。
- 缺失 tenant_id 上下文的查询被数据库拒绝。
- 跨租户负向测试全部通过。

### US-3：MCP 工具安全执行

**作为**集成开发者，**我希望**MCP 工具调用经过验签 + 授权 + 审计，**以便**确信工具契约未被篡改且调用受控。

**验收标准**：
- call_tool 路径强制验签（与 list_tools 一致）。
- 越权调用被拒绝并记录审计事件。
- 能力声明（agent-card）与实测一致。

### US-4：自适应调度可信

**作为**技术决策者，**我希望**"自适应记忆配置选择"有数据证明其优于固定配置，**以便**信任系统推荐并愿意为此付费。

**验收标准**：
- eval harness 产出报告，证明自适应 > 静态最优（统计显著）。
- 或者：诚实降级，产品文案移除"自学习/自进化"，predictor 回退为规则推荐。

### 核心质疑

#### 质疑1：P3 自适应调度的投入产出比——这个需求真的需要做吗？

| 字段 | 内容 |
|------|------|
| **质疑内容** | P3 自适应调度需要 7-11 周（P3a 2-3wk + P3b 3-5wk + P3c 2-3wk + 放行/降级 1wk），在 1-2 名后端 + 兼职 devops/QA 的资源约束下，这是总工期的 30-40%。但 ADR-0008 已明确：如果 eval 无法证明自适应显著优于静态最优，就要"诚实降级"。降级后差异化 = 多层记忆架构 + MCP 生态 + 多协议互操作（D7 决策），意味着 P3 可能投入 7-11 周后仍然回归"启发式配置选择"。 |
| **质疑目标** | P3 自适应调度作为"核心卖点"的定位是否合理 |
| **结论** | **修改** |
| **处理说明** | 1. P3 的核心假设是"自适应 > 静态最优"，但这个假设本身需要 7-11 周才能验证，且存在失败风险。2. 企业买家在技术尽调中最关心的是：数据安全（RLS）、工具安全（MCP）、协议一致性——这些是 P0-P2 的范围。3. **建议**：将 P3 从"核心卖点"降级为"可选增强"，优先级低于 P1/P2；或者将 P3 拆分为两个阶段：P3-lite（配置推荐引擎，3-4 周）和 P3-full（自适应学习，7-11 周），先交付 P3-lite，再根据资源和市场反馈决定是否启动 P3-full。 |

#### 质疑2：资源约束与范围的匹配度——有没有更简单的解决路径？

| 字段 | 内容 |
|------|------|
| **质疑内容** | 资源约束：1-2 名后端 + 兼职 devops/QA，6-12 个月。P1 关键路径 7-10 周 + P2 6-8 周 + P3 7-11 周 = 20-29 周（5-7 个月），还不包括 P0 遗留、缓冲时间和并行任务的协调成本。现有计划虽然已按串行策略降低风险，但总工期粗估偏乐观，且未充分考虑人力不足时的延期风险。 |
| **质疑目标** | 当前路径是否是达成"企业级可售卖"的最简路径 |
| **结论** | **接受**——当前路径是必要的，但需要明确优先级和裁剪空间 |
| **处理说明** | 1. P0-P2 是"企业级可售卖"的硬性要求（数据安全、工具安全、协议一致性），不能裁剪。2. P3 是"差异化卖点"（自适应学习），可以裁剪或推迟。3. **建议**：明确告诉业务方，如果资源不变，P3 可能无法在 6-12 个月内完成；或者将 P3 作为"Phase 2"单独规划，不纳入本轮交付计划。 |

#### 质疑3：用户真实需求 vs 当前方案——用户要的是什么？

| 字段 | 内容 |
|------|------|
| **质疑内容** | 目标用户定义：企业买家（技术尽调场景）、SaaS 运营者（多租户安全）、集成开发者（MCP 工具安全）。成功标准包含"自适应 eval 证明或诚实降级"。但企业买家在技术尽调时真的会验证"自适应优于静态最优"吗？还是更关心：声明与实现一致、跨租户隔离、MCP 安全、协议真实性？ |
| **质疑目标** | 用户要的是"自适应"这个标签，还是要解决"配置选择"这个底层问题 |
| **结论** | **修改** |
| **处理说明** | 1. 企业买家在技术尽调时会验证：RLS 跨租户隔离、MCP 验签+授权、三协议真实受鉴权——这些是 P0-P2 的范围。2. "自适应"是营销标签，不是技术尽调的核心关注点；企业买家更关心"系统是否诚实"（声明 vs 实现一致）。3. **建议**：P3 的成功标准从"eval 证明自适应优于静态最优"改为"配置推荐可解释、可审计、可回退"，降低 P3 的验证门槛，同时保持产品差异化。 |

---

### 替代路径

**替代路径：将 P3 从"自适应学习系统"改为"配置推荐引擎"**

| 字段 | 内容 |
|------|------|
| **当前方案** | P3 = 特征管线 + predictor 拟合 + scheduler 选优 + eval harness，目标是证明"自适应 > 静态最优" |
| **替代方案** | P3 = 基于规则 + 历史数据的配置推荐引擎，目标是"配置选择可解释、可审计、可回退" |
| **理由** | 1. 当前"自适应"本质是启发式 + 写死常量，改为"配置推荐"更诚实。2. 企业买家需要的是"配置选择的可解释性"，不是"自学习"标签。3. 配置推荐引擎可以基于规则 + 历史数据，不需要 ML 验证，工作量从 7-11 周降到 3-4 周。 |
| **收益** | 1. P3 工作量降低 50-60%。2. 成功标准从"eval 证明优于静态最优"改为"配置推荐可解释、可审计"，更易达成。3. 降低 P3 失败风险（不需要 ML 验证）。 |
| **风险** | 1. 产品差异化减弱（失去"自适应/自学习"标签）。2. 需要更新对外文案和营销材料。 |

### 阻断条件

**阻断条件：P1 地基必须在 3 个月内完成，否则整个项目暂停并重新评估**

| 字段 | 内容 |
|------|------|
| **阻断条件** | 如果 P1（tenant_scope + RLS + outbox + 治理 hooks + MCP Plane A + HA 基建）无法在 3 个月内完成，整个项目应暂停并重新评估范围、资源和时间线 |
| **理由** | 1. P1 是企业级可售卖的"地基"（数据安全、工具安全），如果地基不稳，后续 P2（协议）和 P3（自适应）都是空中楼阁。2. 资源约束（1-2 名后端 + 兼职 devops/QA）可能导致 P1 延期，进而影响整个项目时间线。3. 企业买家在技术尽调时会首先验证 P1 的能力（RLS、MCP），如果 P1 无法按时交付，项目可信度将严重受损。 |
| **监控机制** | 1. P1 开始前：确认资源是否足够（是否需要增加人力或缩减范围）。2. P1 进行中：每周检查进度，如果发现延期风险（如 tenant_scope 执行器超出预期），立即升级 tech-lead。3. P1 里程碑检查：PR-1（tenant_scope）完成后评估是否在 3 个月内可完成 P1 全部工作。 |
| **升级路径** | 如果 P1 无法在 3 个月内完成：1. 暂停 P2/P3。2. 重新评估范围（是否需要裁剪 P1 的某些项）。3. 重新评估资源（是否需要增加人力）。4. 与业务方沟通时间线调整。 |

### 假设挑战记录

| 假设 | 挑战内容 | 验证方式 | 结论 |
|------|----------|----------|------|
| **假设1：企业买家会为"自适应"标签付费** | 企业买家在技术尽调时最关心的是数据安全（RLS）、工具安全（MCP）、协议一致性，而不是"自适应"标签 | 市场调研、竞品分析、客户访谈 | **待验证**——建议在 P1/P2 交付后，收集客户反馈再决定是否启动 P3 |
| **假设2：P3 eval 能证明自适应优于静态最优** | ADR-0008 明确指出：如果 eval 无法证明，就要"诚实降级"；且存在选择偏差、数据泄漏等风险 | P3 eval harness 运行结果 | **高风险**——P3 可能投入 7-11 周后仍然失败，建议将 P3 作为"可选增强"而非"核心卖点" |
| **假设3：1-2 名后端 + 兼职 devops/QA 可以在 6-12 个月内完成 P0-P3** | 现有计划粗估偏乐观，未充分考虑人力不足时的延期风险、并行任务的协调成本、以及 P3 的失败风险 | 实际执行进度跟踪 | **高风险**——建议明确 P3 的裁剪空间，或将 P3 作为"Phase 2"单独规划 |

### 结论与下一步

**结论**：
1. P0-P2 是"企业级可售卖"的硬性要求，必须在 6-12 个月内完成。
2. P3（自适应调度）是"差异化卖点"，但投入产出比存疑，建议降级为"可选增强"或改为"配置推荐引擎"。
3. 资源约束（1-2 名后端 + 兼职 devops/QA）是硬限制，需要明确优先级和裁剪空间。
4. 企业买家的真实需求是"数据安全 + 工具安全 + 协议一致性 + 声明诚实"，不是"自适应"标签。

**下一步**：
1. **tech-lead 确认**：P3 是否纳入本轮交付计划？如果纳入，是"自适应学习系统"还是"配置推荐引擎"？
2. **业务方确认**：企业买家是否真的需要"自适应"标签？还是更关心 P0-P2 的能力？
3. **资源确认**：如果 P3 纳入本轮，是否需要增加人力？如果 P3 不纳入，是否可以提前交付 P0-P2？
4. **进入 `/team-plan`**：完成需求挑战会（分组 A/B/C），锁定 P1 执行顺序和资源分配。
