## 上游质疑记录（Product Manager → 业务方）

### 必答问题 ①：这个需求真的需要做吗？不做最坏后果是什么？

**目标**：全线推进 P0-P3 的业务需求本身

**分析**：

P0-P3 全线推进的本质是消除"声明 > 实现"差距。审查发现了 5 大类问题。逐一分析"不做"的后果：

| 问题 | 不做最坏后果 | 是否阻塞售卖 |
|------|-------------|-------------|
| enterprise.rs 假集群 9 个活端点 | 企业买家调用即得到失实结果，构成虚假宣传 | **是**——但只需 P0 收口（1-2 天） |
| MCP 沙箱是 mock、call_tool 不验签 | 工具契约可被篡改、越权调用不被拒 | **是**——P1 Plane A |
| RLS 未接线 | 跨租户数据泄露 | **是**——P1 |
| 三协议是空壳无鉴权 | 企业买家如不检查 gRPC/WS/A2A 则无直接影响 | **否**——REST/MCP 已是真实面 |
| 自适应是启发式+写死常量 | 如不主动宣称"自学习"则无直接法律风险 | **否**——可诚实降级为"规则推荐" |

**结论**：**P0 + P1 是售卖阻塞项，必须做。P2/P3 的紧迫性被高估。** 最坏后果是：若只做 P0+P1，系统在 REST/MCP 上已是"声明=实现"的安全基线产品，可售卖。

### 必答问题 ②：有没有比当前方案更简单的解决路径？

**目标**：业务方描述的"P0→P1→P2→P3 全线串行推进"方案

**分析**：

当前方案是 6-12 个月、P0-P3 全线串行。更简单的路径是：

**"诚实基线优先"路径**：P0 + P1（3-4 个月）→ 发布 v1.0（REST/MCP 企业级）→ 根据客户实际反馈决定 P2/P3 优先级。

理由：
- P2 三协议（gRPC/WS/A2A）当前没有已知客户要求
- P3 自适应即使投入 7-11 周，大概率走向"诚实降级"（ADR-0008 自己承认样本冷启动 + 选择偏差）
- 1-2 名后端 + 兼职 devops/QA 的人力约束下，全线串行意味着每个阶段都处于人力紧张状态

**结论**：**建议修改**——接受"P0+P1 优先"路径，P2/P3 按客户反馈排优先级。

### 必答问题 ③：用户要的是这个具体方案，还是要解决某个底层问题？

**目标**：需求背后的真实动机

**分析**：

业务方要的不是"把 P0-P3 全做完"，而是**"系统能在企业技术尽调中通过"**。这是两个不同的问题：

- "把 P0-P3 全做完" = 修复所有声明>实现差距，包括三协议和自适应
- "企业技术尽调能通过" = 尽调时被检查的路径全部真实

企业技术尽调的典型检查路径：
1. 代码扫描 → P0 清理解决
2. 多租户安全 → P1 RLS 解决
3. API 安全 → P1 MCP Plane A 解决
4. 数据可靠性 → P1 outbox + HA 解决
5. 调用 REST/MCP API → 已是真实面

**P2/P3 在技术尽调中的检查概率远低于 P1。** 大多数企业买家不会检查 gRPC/WS/A2A 是否真实实现，除非他们明确要求这些协议。自适应调度的"学习能力"更不可能在尽调中被深入审查。

**结论**：**建议修改**——从"全线推进"调整为"尽调阻塞项优先"，P2/P3 作为 v2 路线图。

## 替代路径

### 替代路径："尽调安全基线"分两阶段交付

| 阶段 | 范围 | 时间 | 放行标准 |
|------|------|------|----------|
| **v1.0 企业基线** | P0 收口 + P1 全部（RLS/outbox/治理/MCP Plane A/HA） | 3-4 个月 | 技术尽调所有常见检查项通过；跨租户隔离 DB 层强制；MCP 安全；备份恢复演练 |
| **v1.5 协议扩展** | P2（根据客户反馈排序）| 2-3 个月 | 按需补真——如有客户要求 gRPC 集成则先做 gRPC |
| **v2.0 智能增强** | P3（根据 v1.0 生产数据决定）| 视数据 | 若积累足够样本且 eval 证明增益→放行；否则永久保持"规则推荐" |

**为什么不选当前方案**：
- 1-2 名后端 + 兼职 devops/QA，6-12 个月全线推进，每阶段人力都紧张，风险集中在"全部做完但每项都半吊子"
- P3 的"诚实降级"概率高（ADR-0008 自己承认），投入 7-11 周大概率产出的是"我们证明了自适应目前没有用"——这在 v1.0 发布后用生产数据验证成本更低
- P2 三协议没有已知客户驱动，属于"预设需求"

**为什么当前方案仍可接受（但需修正）**：如果业务方确认已有明确客户要求 gRPC/A2A 集成，或有明确的差异化竞争理由需要"自适应"标签，则 P2/P3 优先级可上调。但**必须有具体客户/市场证据**，而非"架构完整性"驱动。

## 核心质疑（需求挑战会）

### 质疑 1：P2 多协议的用户价值被高估——没有已知客户要求

| 项目 | 内容 |
|------|------|
| **质疑内容** | P2（gRPC/WS/A2A 接真实 + 鉴权）在当前资源约束下是否值得在 v1 范围内推进？是否有任何已知企业客户明确要求这些协议的真实实现？ |
| **质疑目标** | PRD "In Scope" 第 3 条（P2 多协议）和 delivery-plan P2 里程碑 |
| **结论** | **修改**——建议将 P2 从 v1 主线移至 v1.5，按客户反馈排序 |
| **处理说明** | ADR-0007 详细设计了四协议统一鉴权架构，设计质量高，但**设计就绪≠需求紧迫**。当前只有 REST/MCP 是真实面且已有鉴权。gRPC/WS/A2A 是空壳，但**除非有客户要求这些协议的集成**，否则在 1-2 名后端人力下，P2 的 6-8 周投入产出比低于将这些人力投入 P1 强化或技术债清理。如果业务方能提供具体客户或 RFP 要求 gRPC/A2A 集成的证据，则可恢复为 v1 范围 |

**反例分析**：
- 不做 P2 最坏影响：有客户要求 gRPC 集成时无法响应，可能丢单。但此风险可通过"架构设计已就绪（ADR-0007）、实现可快速启动"缓解
- 做错 P2 最坏影响：gRPC/WS 实现有安全漏洞（鉴权绕过），比不做更危险——ADR-0007 明确了"不得以壳冒充"

### 质疑 2：P3 自适应投入 7-11 周，大概率产出"诚实降级"

| 项目 | 内容 |
|------|------|
| **质疑内容** | P3 的成功标准是"eval 证明自适应 > 静态最优（统计显著）"。在以下现实约束下，达成此标准的概率有多高？(a) 生产样本极少（系统尚未大规模部署）；(b) 离线基准需要"全因子实测"（任务×配置），成本高；(c) ADR-0008 自己承认"off-policy confounding"需要探索机制，但探索在企业场景中难以实施 |
| **质疑目标** | PRD US-4 验收标准（eval 证明优于静态最优）和 ADR-0008 放行标准 |
| **结论** | **修改**——建议将 P3 从 v1 主线移至 v2，基于 v1 生产数据积累后再决定；v1 保留"规则推荐 + 诚实标注" |
| **处理说明** | ADR-0008 的设计非常严谨（eval 方法论、防泄漏、诚实降级），但这恰恰说明了"证明自适应有用"的门槛很高。1-2 名后端 + 兼职 QA 在 7-11 周内同时完成特征管线、模型训练、eval harness、统计显著性验证，概率不高。更务实的做法是：v1 保持启发式 + 诚实标注"基于遥测的规则推荐"，在 v1 生产运行中积累真实样本，v2 用真实数据验证是否有增益 |

**反例分析**：
- 不做 P3 最坏影响：失去"自适应"差异化卖点。但 ADR-0008 已经给出了降级路径——"基于遥测的规则化配置推荐"仍然比竞品的"静态配置"强，且诚实标注不会损害企业信任
- 做错 P3 最坏影响：eval 不严谨导致虚假证明"自适应有效"——这是比不做更严重的企业内控问题（ADR-0008 "诚实性红线"）

**苏格拉底三问**：
- **Evidence**：有没有证据表明当前的启发式策略表现差到必须用学习替代？——没有。当前 `PerformancePredictionModel` 的常量是基于"合理假设"的，虽然不是"真学习"，但在没有对照实验前不能假定它"不行"
- **Reasoning**：为什么 P3 必须在 v1 中完成？——PRD 说"企业技术尽调"，但技术尽调不太可能深入审查 ML 管线的统计显著性
- **Implications**：如果 P3 失败（eval 无法证明增益），7-11 周的投入产出是什么？——一个详细的"诚实降级"报告。这有价值，但不值 7-11 周的 1-2 名后端全力投入

### 质疑 3：enterprise.rs 假集群在 P0/P2 之间的"摘除但保留"策略存在文档漂移风险

| 项目 | 内容 |
|------|------|
| **质疑内容** | 决策 D1 说"从路由摘除但保留文件，P2 做真复用"。但 delivery-plan 原始版本说"P0 删除，P2 重新实现"，后被用户决策改为"不删做真"（ADR-0006）。2026-08-03 新 PRD 又说"从路由摘除"。三种不同方向在两个 delivery-plan 中交叉存在，团队成员可能看到不同版本的文档 |
| **质疑目标** | 两个 delivery-plan（2026-07-16 和 2026-08-03）对 enterprise.rs 的处理决策不一致 |
| **结论** | **要求上游修改**——需在单一文档中统一 enterprise.rs 的最终处置方案，消除两个 delivery-plan 之间的决策冲突 |
| **处理说明** | 2026-07-16 delivery-plan 的"决策更新"明确说"R4 反转：不删做真"，P0 不再执行删除。2026-08-03 新 PRD 说"enterprise.rs 假集群从路由摘除（保留文件）"并纳入 P0 收口。这两个决策不完全矛盾（一个是"不删"，一个是"摘路由但不删文件"），但**方向不同、阶段不同**，如果工程师只看到一个文档会执行错误方案。建议：在 2026-08-03 PRD 中显式注明"D1 覆盖了 2026-07-16 的 R4 反转决策"，并废弃或标注旧文档 |

**反例分析**：
- 不统一文档最坏影响：工程师按旧文档操作，误删 enterprise.rs（与"保留文件做真"矛盾），或遗漏摘路由（9 个假端点继续暴露）
- 做错统一最坏影响：无——统一是纯文档行为，不改代码

### 质疑 4：资源约束假设过于乐观

| 项目 | 内容 |
|------|------|
| **质疑内容** | PRD 说"1-2 名后端 + 兼职 devops/QA，6-12 个月"。delivery-plan 的时间估算：P0 1-2 天 + P1 关键路径 7-10 周 + P2 6-8 周 + P3 7-11 周 = 20-29 周（不含缓冲），即 5-7.5 个月。1 名后端承担 P0-P3 全部实现（54 个 services 文件、8 篇 ADR 的全部落码），每个阶段之间无缓冲，且 QA/devops 是兼职——这意味着测试和运维保障质量无法保证 |
| **质疑目标** | PRD 资源约束部分和 delivery-plan 时间估算 |
| **结论** | **升级给 tech-lead**——需要确认实际可用人力，并按人力校准范围或时间 |
| **处理说明** | 如果实际只有 1 名后端 + 兼职 QA，建议：(a) 严格砍 P2/P3 到 v2（节省 13-19 周），或 (b) 接受 12 个月的时间线且允许每个阶段有 1-2 周缓冲，或 (c) 增加人力到 2 名后端 + 1 名全职 QA。三选一，不能"1 人 + 兼职 QA + 6 个月 + 全线推进"同时成立 |

## 需求假设挑战记录

### US-1（企业买家技术尽调）

| 假设 | 挑战 | 结论 |
|------|------|------|
| **假设 A**：企业买家会检查 gRPC/WS/A2A 是否为真实实现 | **挑战**：大多数企业技术尽调聚焦 REST API 文档、安全审计、数据隔离证明，不会逐协议检查所有传输层实现。除非客户明确要求 gRPC/A2A 集成 | **已验证**：无具体客户证据表明需要检查三协议→P2 降级为 v1.5 |
| **假设 B**：消除所有"声明>实现"是技术尽调的必要条件 | **挑战**：技术尽调是抽查而非穷举。如果 REST/MCP 面已全部真实、RLS 已生效、MCP 安全已落地，尽调大概率通过。P2/P3 的"声明>实现"在尽调中被发现的概率较低 | **已验证**：概率分析成立→P0+P1 覆盖尽调主要检查路径 |

### US-2（多租户数据安全）

| 假设 | 挑战 | 结论 |
|------|------|------|
| **假设 A**：RLS 迁移（expand→backfill→enforce）可以在现有离线环境中完整验证 | **挑战**：ADR-0001 明确说需要"真 PG 可写实例"，ADR-0005 说需要"Testcontainers 集成测试环境"。当前离线会话只有静态分析。迁移在离线环境中只能验证语法，不能验证 RLS 行为 | **接受**：这是一个合理的硬约束，需要真实环境。已在 delivery-plan 风险表中识别 |
| **假设 B**：应用层 TenantId 校验 + RLS 三层防线足够 | **挑战**：ADR-0001 说"t:{tenant} prefix 在迁移期可作为 backfill 依据"。backfill 过程中，历史数据的 tenant_id 归属是否准确？无法归属的数据如何处理？ | **已验证**：ADR-0001 §兼容性已覆盖——"历史无法归属数据需要 quarantine 或只读隔离" |

### US-3（MCP 工具安全执行）

| 假设 | 挑战 | 结论 |
|------|------|------|
| **假设 A**：Plane A（验签+授权+审计）足够当前企业售卖，不需要 Plane B（wasmtime 真沙箱） | **挑战**：如果企业买家自带/要求集成第三方 MCP 工具，Plane A 不够——ADR-0004 明确说"对不可信工具只验签是失守" | **已验证**：当前无不可信工具场景→Plane A 足够；Plane B 可推迟 |
| **假设 B**：现有 HMAC-SHA256 签名机制足够安全 | **挑战**：对称密钥（HS256）意味着验证方和签名方共享同一密钥。如果密钥泄露，任何调用者可伪造签名。ADR-0004 提到"评估 signing key bundle 与集团统一密钥/制品签名平台对接"——但此评估未完成 | **已验证**：作为 v1 基线可接受；需在后续迭代评估非对称签名或集团密钥管理集成 |

### US-4（自适应调度可信）

| 假设 | 挑战 | 结论 |
|------|------|------|
| **假设 A**：自适应调度是企业买家的核心购买决策因素 | **挑战**：企业买家购买 AI Agent 记忆管理系统的核心诉求是"可靠、安全、可审计"，而非"自学习"。ADR-0008 的诚实降级路径说"差异化 = 多层记忆 + MCP 生态 + 多协议互操作"——这本身就说明"自适应"不是唯一差异化 | **已验证**：自适应是锦上添花而非刚需→P3 优先级应低于 P1 |
| **假设 B**：离线全因子基准数据集可以代表真实生产场景 | **挑战**：ADR-0008 说基准集"按 complexity/modality/reasoning 分层"。但真实生产中的任务分布可能与基准集不同（长尾分布、领域特定、用户行为模式）。基准集上的结论不一定能泛化到生产 | **已验证**：这是所有离线 eval 的固有局限。ADR-0008 已通过"分层报告 + win-rate + CI"部分缓解，但不能完全消除。此风险在 P3 降级到 v2 后，可用真实生产数据补充验证 |

## 结论、风险、待确认项、下一步

### 结论

1. **P0 + P1 是售卖阻塞项**，必须在 v1 中完成。
2. **P2/P3 的紧迫性被高估**，建议降级为 v1.5/v2，按客户反馈排优先级。
3. 两个 delivery-plan 之间对 enterprise.rs 的决策存在文档漂移风险，需统一。
4. 资源约束（1-2 后端 + 兼职 QA，6-12 个月）需 tech-lead 确认实际可用人力后校准范围。

### 风险

| 风险 | 影响 | 缓解 |
