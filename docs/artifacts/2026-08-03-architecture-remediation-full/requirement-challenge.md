## 结论先行

1. 本次全线推进（P0→P3）**方向正确**，但 PRD 和 delivery-plan 存在 3 个需要裁决的核心质疑。
2. **最大风险不是技术，是资源与范围的错配**：1-2 名后端 + 兼职 devops/QA 在 6-12 个月内完成四阶段修复 + 产出 eval 证据，人力严重不足。
3. **P3 自适应的"成功标准"定义过于刚性**，可能成为团队最大的时间黑洞。
4. 建议新增 1 条**阻断条件**：若 P1 地基未通过 QA 放行，P2/P3 绝对不可启动。
5. 存在 1 条**替代路径**：将 P3 降级为独立产品线，不阻塞核心系统的企业级售卖。

## 上游质疑记录

> 依据 `rules/handoff-contract.md` 要求，接收方（product-manager）必须对上游输入提出质疑。

### 质疑 1：全线推进（P0→P3）的时间承诺是否可信？

- **质疑内容**：delivery-plan 给出 P0（1-2天）→ P1（7-10周）→ P2（6-8周）→ P3（7-11周）的粗估，总跨度约 16-21 周（4-5个月），但资源约束声明"6-12个月"。这两个数字之间存在巨大弹性——如果取乐观估值，我们向业务方承诺 4 个月；如果取悲观估值，则是一年。请问：**我们到底要向市场承诺什么时间窗口？这个承诺是否有任意阶段超期的退出策略？**
- **质疑目标**：PRD 的「资源约束」与 delivery-plan 的「粗估时间」之间的不一致
- **结论**：**要求上游修改**——PRD 需要明确每个阶段的"承诺截止"与"弹性截止"，以及超期退出策略
- **处理说明**：
  - 乐观估算假设一切顺利（RLS 迁移无遗漏、MCP 验签无误拒、P3 eval 一次通过），4-5 个月完成。
  - 但 RLS 迁移的 delivery-plan 自己也说"易遗漏查询导致隔离绕过"，P3 eval 的 ADR-0008 明确给出了"诚实降级"路径——说明团队预期失败概率不低。
  - **修正建议**：PRD 应将成功标准分为"硬承诺"（P0+P1 完成 = 企业可售卖的最低门槛）和"差异化目标"（P2+P3 = 竞争力增强），分别给出时间承诺。
  - **关键洞察**：P0+P1 完成后系统已经满足企业技术尽调的底线需求（声明一致 + RLS 隔离 + MCP 验签）。P2/P3 是锦上添花，不是售卖前提。

### 质疑 2：三条目标用户故事是否在同一优先级？

- **质疑内容**：PRD 列出三条用户故事——企业买家（技术尽调）、SaaS 运营者（多租户安全）、集成开发者（MCP 工具安全）。但这三类用户的**紧迫度和付费意愿完全不同**。企业买家做技术尽调是**售前门槛**——过不了这关，后面的多租户安全和 MCP 安全都无人问津。而"自适应调度可信"（US-4）是**差异化卖点**——有了更好，没有也不影响基本售卖。**请问：我们是否应该把 US-1 和 US-2 标记为 P0/P1 的硬门槛，而 US-3 和 US-4 标记为"增强目标"？**
- **质疑目标**：PRD 的用户故事优先级均质化问题——四条 US 看似平等，但实际商业价值差异巨大
- **结论**：**要求上游修改**——PRD 需要对用户故事做显式优先级分级
- **处理说明**：
  - **US-1（企业买家技术尽调）= P0 绝对阻塞项**：没有这个，产品卖不出去。P0 清理 enterprise.rs 假端点 + 文档诚实化即满足。
  - **US-2（多租户数据安全）= P1 硬门槛**：RLS 强制隔离是 SaaS 售卖的法律/合规底线。不通过 = 不可售卖。
  - **US-3（MCP 工具安全）= P1 增强项**：Plane A（验签+授权）是安全底线；Plane B（wasmtime 真沙箱）可降级为 P2（ADR-0004 已论证当前无不可信工具）。
  - **US-4（自适应调度可信）= P2/P3 差异化目标**：不影响基本售卖，影响定价和市场定位。
  - **修正建议**：PRD 用户故事部分应增加优先级标签（Blocker / Must-Have / Should-Have / Nice-to-Have），并与 P0-P3 阶段显式对齐。

### 质疑 3："成功标准 = 声明与实现 100% 一致"是否可操作？

- **质疑内容**：PRD 成功标准第 1 条写"grep '声明>实现' = 0"。这是一个**文案级检查**，不是**行为级验证**。我们可以把所有"自适应/自进化"字样从文档里删掉（P0 已部分完成），但用户在技术尽调中实际做的是**跑 API、读代码、验证行为**——他们不会只看文档里有没有"自适应"这个词。**请问：成功标准是否应该从"文档无虚假声明"升级为"API 行为可被第三方独立验证"？**
- **质疑目标**：PRD 成功标准的可验证性——当前定义过于依赖"文案清理"而非"行为验证"
- **结论**：**接受原方案，但需补充**——保留"声明一致"作为 P0 成功标准，但 P1 起的成功标准必须升级为行为级验证
- **处理说明**：
  - P0 阶段的"声明一致"检查是合理的——它解决的是最低门槛信任问题（"文档不骗人"）。
  - 但从 P1 起，企业买家的技术尽调是**跑测试**不是**读文档**。所以 P1 的成功标准（"跨租户负向测试通过""MCP 验签通过"）已经是行为级的，这部分没问题。
  - **需要补充的是**：P3 的成功标准"eval 报告产出"过于模糊——应该明确"eval 报告必须可被第三方在相同数据集上复现"，否则企业买家会质疑 eval 结果的可信度。
  - **修正建议**：在 P3 成功标准中增加"eval 报告 + 数据集 + 代码可复现，第三方可在相同条件下跑出相同结论"。

## 替代路径

### 替代路径：P3 拆分为独立产品线，不阻塞核心系统售卖

**当前路径**：P0→P1→P2→P3 严格串行，P3 是售卖系统的"差异化卖点"。

**问题**：
1. P3 的时间估算（7-11周）是四阶段中最不确定的——ADR-0008 自己给出了完整的"诚实降级"路径，说明团队预期失败概率不低。
2. 1-2 名后端的资源约束下，P3 的 ML/数据工程工作（特征管线、离线训练、eval harness）需要的数据工程技能可能不在团队能力范围内。
3. P3 串行在 P2 之后，如果 P2 超期，P3 会被进一步压缩。

**替代路径**：
1. **P0+P1 完成后即启动企业售卖**——此时系统已满足企业技术尽调底线（声明一致 + RLS 隔离 + MCP 验签）。
2. **P2 作为"多协议增强"独立排期**——gRPC/WS/A2A 接真实是功能增强，不是售卖前提。
3. **P3 作为"自适应调度"独立产品线**——单独组建（或外包）数据工程能力，不占用核心系统的人力瓶颈。
4. **核心系统的差异化先靠"多层记忆架构 + MCP 生态 + 企业级安全"打**——这些都是 P0+P1 已经交付的。

**为什么不选这个路径**：
- 业务方可能已对外承诺"自适应调度"是核心卖点，降级会影响市场定位。
- 团队可能希望保持技术完整性，不愿意"半途而废"。

**建议**：由 tech-lead 和业务方共同裁决。如果业务方可以接受"先卖基础能力，再迭代差异化"，则此路径可显著降低风险。

## 阻断条件

### 阻断条件：P1 地基未通过 QA 放行，P2/P3 绝对不可启动

**定义**：以下任一项未通过，P2/P3 的任何工作都必须停止：

1. **跨租户负向测试通过**（所有 memory-owned tables）——证明 RLS 隔离有效。
2. **MCP call_tool 验签 + 越权拒绝负向测试通过**——证明 Plane A 安全有效。
3. **备份/恢复演练通过**（PG + Qdrant）——证明数据可恢复。
4. **治理 hooks 接线验证通过**——证明 RBAC/配额/审计生效。

**理由**：
- P1 是"企业售卖准入底线"（delivery-plan 原文）。在地基不稳的情况下推进 P2（多协议）会扩大攻击面（更多协议 = 更多未鉴权入口），推进 P3（自适应）会在不可靠的数据基础设施上建 ML 管线。
- 历史教训：P0 的 enterprise.rs 假端点就是"地基未稳就对外暴露"的典型案例——9 个假端点在 P0 清理后仍未完成，说明如果不设硬阻断，遗留项会一直拖下去。

**执行方式**：
- P1 每个 PR（PR-1 到 PR-8）合并前必须通过对应的负向测试。
- P1 全部完成后，由 tech-lead 主持 P1 放行评审，QA 出具放行报告。
- 放行报告未签署前，P2 的任何代码提交（包括"预研"性质的提交）都不允许合并到主分支。
